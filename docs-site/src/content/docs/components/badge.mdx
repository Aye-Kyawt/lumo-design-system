### `use_when`

**Both sources agree, in the same words.** Figma's description on the `Badge`
component set reads *"Use a badge to label a status or category the user reads,
not clicks — a category tag, a status pill, a 'Most popular' flag."*
`badge.jsx` and `docs/badge.md` both quote it verbatim.

This is the most decided `use_when` of the six components documented here: it
names the job (label a status or category), the mode (read, not clicked) and
three concrete examples.

### `dont_use_when`

**Both sources agree, in the same words.** Figma: *"Don't use it for something
the user can interact with; use Chip for that."* The repo quotes the same
sentence.

**The replacement exists in Figma and not in the repo.** `chip` is a published
component set in the Lumo.Web library, and its own description closes the loop
— *"Don't use a chip as a status label — that is a Badge."* There is no chip in
`src/components/`, so a developer following Badge's documented advice has
nothing in this library to follow it to.

### `variant_intent`

**The shape is agreed.** One variant property, `Tone`, with five values —
`primary`, `success`, `warning`, `danger`, `neutral`. No size property and no
state property, in either source.

**What each tone is *for* is stated by neither source.** No variant inside
`17:1139` carries a description, and the repo describes mechanics only:
`badge.jsx` says `tone` *"picks the tonal surface and the label colour."* Which
tone a given status should take has not been written down.

The repo's `In context` story illustrates one reading — primary for "Most
popular", success for "Available", warning for "2 rooms left", danger for "Sold
out", neutral for "Unlisted" — and the primary example matches the *"Most
popular" flag* that Figma's own description names. But a story is an
illustration, not a rule, and neither source states it as one.

**Why there are no interaction states, and both sources agree on it.** The set
defines no hovered, pressed, focused, disabled, error or loading variant.
`docs/badge.md` treats that as correct rather than missing, and reasons from
Figma's own description: a badge is read, not clicked, so the component renders
as a `<span>`, takes no `onClick`, and is not focusable. Adding a hover or focus
affordance would advertise an interaction that does not exist.

### `placement`

**Neither source states where a Badge belongs in a layout.** Badge's own Figma
description says nothing about placement, and neither does the repo.

Four other Figma components place one, in their own documentation:
`card/header` (*"an Action slot for a button, badge or avatar"*),
`card/layout/metric` (*"a ↳Badge slot for the change"*), `table/cell` (*"Drop
text, a badge, an avatar, a checkbox or a button into the ↳Content slot"*), and
`kanban/card` (*"a category badge … and either a due-date text or a status
badge"* — which also carries the only placement *prohibition* anywhere near
Badge: *"Don't show both Meta and Status at once; pick whichever applies."*).
Those are statements by those components about themselves, listed as evidence
rather than promoted into Badge's own rule.

### `pairs_with`

**Figma, from sibling documentation.** `card/header`, `card/layout/metric`,
`table/cell`, `kanban/card`, and `marketing/pricing-card` (*"the dark 'most
popular' tier with a badge"*). `chip` is named as the alternative, not a pair.
`Avatar` mentions Badge as what a company, bot or system account reads better
as — a substitution, not a pairing.

**Repo.** `badge.stories.jsx` imports nothing but `Badge` itself. Its `In
context` story puts badges beside plain text, not inside any other component.

**So the two sources differ in kind, not in content.** Figma documents five
host components for a badge; the repo demonstrates none of them, because four
of the five (`card/layout/metric`, `table/cell`, `kanban/card`,
`marketing/pricing-card`) have no code at all, and the fifth (`card/header`)
fills its action slot with a placeholder.

### `required_tokens`

Read live from `get_variable_defs` on `17:1139` and from `badge.css`. Both
sources carry the same set.

| Property | Token |
|---|---|
| Corner radius | `border/radius/chip` |
| Padding, block | `spacing/padding/xs` |
| Padding, inline | `spacing/padding/sm` |
| Label type | `Label/Label1` |

Per tone, a tonal surface and a label colour: `bg/primary/tonal/idle` +
`text/brand`; `bg/positive/tonal/idle` + `text/positive`;
`bg/warning/tonal/idle` + `text/orange/twoTone`; `bg/negative/tonal/idle` +
`text/red/twoTone`; `bg/surfaceSecondary` + `text/secondary`.

**The horizontal padding gap is closed, and the live read confirms it.**
`docs/badge.md` reports that the node originally carried a raw unbound 10px
there, and that the designer has since bound `paddingLeft`/`paddingRight` to
`spacing/padding/sm` — the token the component had already chosen. Reading
`17:1139` live today returns `--lumo-semantic-spacing-padding-sm` at `8`, so
code and design now agree at token level and not merely by eye.

**Both padding tokens are mode-dependent**, which is the tokens working rather
than a defect: `padding/xs` is 4 in web and mobile and **2** in admin,
`padding/sm` is 8 and **4**. So the badge measures 60.67×24 in web and mobile
and 52.67×20 in admin. The Figma node is drawn in the web mode alone, so anyone
comparing an admin rendering against it will see a difference that is correct.

**All five tones clear WCAG AA**, measured foreground on their own tonal
surface — Danger 8.92, Warning 6.72, Primary 5.43, Neutral 4.84, Success 4.57.
Two of them only after two rounds of rebinding, documented in `docs/badge.md`.

**One live reading neither source explains.** `get_variable_defs` on `17:1139`
returns, alongside the sixteen Lumo semantic variables, a bare
`color/primary: #5b4cf5`. That is not a Lumo token — `#5b4cf5` appears nowhere
in the component, the build report or the generated CSS. `17:1139` is a wrapper
frame around the five variants, so it most likely belongs to the frame rather
than to any badge, but neither source says what it is. Reported, not resolved.

**An open design question, recorded and not decided.** Badge currently
straddles two token tiers: Warning and Danger sit on `twoTone`, Primary and
Success on the general text tier, Neutral on `text/secondary`. Moving Primary
to `text/aqua/twoTone` would take it from 5.43 to 8.68 and is a visible change;
moving Success would change nothing, because `text/positive` and
`text/green/twoTone` resolve to the same primitive. Neutral has no `twoTone`
counterpart at all. `docs/badge.md` records the whole table. Nobody has decided.

### `anatomy`

*The field name is unconfirmed — see the note at the top of this section.*

**Both sources agree on the parts, and there are only two.** A hug auto-layout
pill holding one text layer. Figma names the layer `Label` — 45×16 at x=10, y=4
inside a 65×24 variant — and the repo renders a `<span class="lumo-badge">`
wrapping a `<span class="lumo-badge__label">`. The `label` prop is that layer.

The set has no sub-components and imports nothing, in both sources: `Composes`
in the registry is empty and `badge.jsx` imports only its own stylesheet.

design gaps are in the build report,

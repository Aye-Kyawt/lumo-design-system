# tools.md - what this project is built with

Stack facts and commands only. Rules about how we work live in 'CLAUDE.md'.

## Stack

- Framework : React 19 with Vite
- Language : JavaScript with JSX. `typescript` **is** now installed at the repo root and there
  **is** a root `tsconfig.json`, added when the repo became a publishable package — but only so
  `tsup` can emit `.d.ts` from the JSDoc on the `.jsx` sources and so `npm run typecheck` is a
  real command. `checkJs` is off and no source file is `.ts` except `src/index.ts`, which is a
  ten-line export list. This is still not a TypeScript repo. `docs-site/` has its own
  `tsconfig.json`, because Astro ships its own TypeScript and Starlight's content config is a
  `.ts` file; that does not make this a TypeScript repo either.
  A component is `src/components/<name>/<name>.jsx` with `<name>.css`, `<name>.stories.jsx` and an
  `index.js`; subcomponents sit beside it in the same folder, camelCase (`buttonIcon.jsx`)
- Package manager : npm
- Tests : Vitest 3 in jsdom, with Testing Library. Config at `vitest.config.js`, setup at
  `src/test/setup.js`, shared render helper at `src/test/renderWithTokens.jsx`. One
  `<name>.test.jsx` beside each public component, plus `src/index.test.js` for the public
  surface and `src/test/dist.test.js` for the built package
- Library build : `tsup` 8, config at `tsup.config.js`. One entry, `src/index.ts`; ESM + CJS +
  `.d.ts`; `react` and `react-dom` external. Output `dist/`, gitignored
- Published package : scoped, `@ds-house/lumo-design-system`, at `0.1.0`. `private: true` sits
  in `package.json` as a guard so a stray `npm publish` is refused; `npm run release:publish` is
  the only command that lifts it, and it puts it straight back
- Styling : CSS custom properties, generated from tokens
- Tokens : Style Dictionary v5, driven by `build-tokens.js`, reading the Figma "Design Tokens" plugin export
- Component workshop : Storybook 10 (react-vite)
- Reference site : Astro 7 with Starlight 0.42, in `docs-site/`. It has its **own**
  `package.json` and its own `node_modules`, and is not a workspace of the root project

## Commands
| Job | Command |
|---|---|
|Install | `npm install` |
|Build tokens | `npm run build:tokens` |
|Build the library | `npm run build:lib` (tsup → `dist/`) |
|Stage the stylesheets | `npm run build:css` (→ `dist/styles.css`, `dist/tokens.css`) |
|Build the whole package | `npm run build:package` (tokens → library → CSS, in that order) |
|Type check | `npm run typecheck` (`tsc --noEmit`) |
|Tests | `npm test` (`vitest run`) |
|Tests, watching | `npm run test:watch` |
|Cut a release | `npm run release:publish -- <version> [--dry-run]` |
|Run Storybook | `npm run storybook` |
|Build Storybook | `npm run build:storybook` (outputs `storybook-static/`) |
|Install the reference site | `npm --prefix docs-site install` |
|Run the reference site | `npm --prefix docs-site run dev` (port 4321) |
|Build the reference site | `npm --prefix docs-site run build` (outputs `docs-site/dist/`) |

The reference site's `dev` and `build` both run the root `build:tokens` first, the same
way `build:storybook` does, so its token CSS is generated and never committed.

- Skills : `.claude/skills/`

## Repo root deployment — Storybook
- Vercel project : imported from this repo with the repo root as its root directory. It publishes
  **Storybook**, which is the only thing this repo builds
- Build config : `vercel.json` at the root — `framework: null`, `npm install`,
  `npm run build:storybook`, output `storybook-static`
- `framework: null` is the part that matters. Left to detect, Vercel sees `vite` in
  devDependencies, applies its Vite preset and runs `vite build`, which looks for an `index.html`
  entry at the root. A component library has none, so Rollup resolves zero entry modules and the
  build fails with `Command "vite build" exited with 1`. Setting the framework to Other stops
  that. Reproduce the failure with `npx vite build`
- Install is `npm install`, not `npm ci`: a lockfile written on macOS can omit packages Linux
  needs, and `npm ci` refuses it
- `npm run build:storybook` runs `build:tokens` first, so the generated token CSS that
  `.storybook/preview.jsx` imports from `build/css/` is produced during the build. Nothing
  generated needs to be committed for the deploy to work — verified from a clean tree with
  `build/`, `.tokens-clean/` and `storybook-static/` all absent
- Previews and production : every branch gets a preview URL, `main` gets production. These are
  the URLs the registry's `Staging Storybook` and `Production Storybook` columns are for — a
  preview build for the Engineer, the production build for DevOps. Both agents must still open
  the URL and see it render before writing the cell; a link to a build nobody looked at is a lie
  in a cell
- History : the root carried `{"git": {"deploymentEnabled": false}}` while no project was meant
  to build it. Note for anyone re-reading that period — the flag only suppresses deployments
  triggered by a **git push**. Importing a project, or deploying from the dashboard or the CLI,
  is not a push and builds regardless

### Why the config differs per branch

`docs-site/vercel.json` is **not the same file on every branch**, on purpose:

- on `astro` — the real build config (framework, install, build, output)
- everywhere else, `main` and `staging` included — only `{"git": {"deploymentEnabled": false}}`

The reason is that the docs project watches the whole repo. Without this, every push to every
branch asks it for a deployment and hangs a check on the PR. `deploymentEnabled: false` is read
from the branch being pushed, so a push to `main` finds the flag and stops; a push to `astro`
finds the real config and builds production.

Three things about this are easy to get wrong:

1. **It only works because Root Directory is `docs-site`.** Vercel reads `vercel.json` *from the
   root directory*. Had the project still been pointed at the repo root, `docs-site/vercel.json`
   would be a file it never opens, on any branch, and this flag would be inert. Verified working
   rather than assumed: the commit carrying the flag produced **no reference-site deployment at
   all**, while the previous commit on `staging` (`9970566`), without it, produced one. The
   repo-root Storybook project deployed normally on both, which is correct — it reads the root
   `vercel.json` and this change does not touch it
2. **The flag only suppresses deployments triggered by a git push.** Importing a project, or
   deploying from the dashboard or the CLI, is not a push and will build regardless — the same
   note already recorded against the repo root. A manual deploy from `main` would therefore run
   with no framework, build command or output directory, and should be expected to fail. That is
   not a bug to chase; it is this file doing its job
3. **`astro` and `main` now conflict on this file forever.** Every merge in either direction hits
   it. `astro` carries no other commits of its own — at the time of writing it is the same commit
   as `origin/main` — so keeping it current means merging `main` into it and keeping `astro`'s
   side of `docs-site/vercel.json` each time. A future alternative worth considering is dropping
   the per-branch split and using the project's own ignored-build-step setting instead, which
   would keep one config in the repo

### Why Astro and Starlight were added

Two dependencies, `astro` and `@astrojs/starlight`, both in `docs-site/`, neither at the root.

They were not added to solve a problem the existing stack already solves. Storybook renders
components; it does not carry intent — when to reach for a component, when not to, what it
pairs with. `.claude/agents/doc-generator.md` names "the Astro Starlight site" as the thing it
writes, and the registry's `Astro Link` column is a cell with nowhere to point. Six components
currently sit at `Completed` with a `Blocked` release verdict, and the first reason in all six
reviews is that no reference page exists and no site exists to hold one.

Keeping them out of the root `package.json` is deliberate. The root carries `vite` for
Storybook and Astro bundles its own; one `node_modules` for both invites a hoisting conflict
in the only build that currently reaches production.

## Why Vitest was added, and what the suite does not cover

**`vitest`, `@testing-library/react`, `@testing-library/jest-dom`, `jsdom`** — four root dev
dependencies.

Vitest rather than Jest because Vite 7 is already at the root for Storybook, so Vitest reuses
the transform pipeline and the `@vitejs/plugin-react` that is already installed. Jest would have
needed its own Babel setup for JSX on top of a toolchain that already does it. The config is a
separate `vitest.config.js` for the same reason `tsup` has its own file: the root Vite config is
load-bearing for the only build that reaches production.

There was no test command to reuse, so this did not displace anything.

### What it covers

One `<name>.test.jsx` beside each of the ten public components, covering every variant and every
state the component actually exposes, the fallback when an unknown value is passed, and the
behaviour the design implies — a switch that flips, an accordion that discloses, a card that is
operable by keyboard only when it has an `onClick`, a disabled control that refuses. Plus
`src/index.test.js`, which asserts the public surface is exactly ten names and that none of the
eleven internal components has leaked into it, and `src/test/dist.test.js`, which loads the
**built** ESM and CJS bundles, renders from them, and checks the declarations and both
stylesheets.

### What it deliberately does not cover

- **No computed colour, spacing, radius or font assertions.** jsdom does not resolve CSS custom
  properties across sheets, so such a test could only pass by hardcoding a token's value — which
  is a second place for that value to live, and the drift tokens exist to prevent. Visual
  fidelity is the Storybook QA pass's job, against the Figma node.
- **Not a substitute for that QA pass.** These tests compare a component against its own
  documented API. They agree with the code by construction and cannot tell you the component
  matches its design. `.claude/skills/test/SKILL.md` is the pass that can.
- **No accessibility audit.** The tests assert the specific semantics each component documents —
  roles, `aria-checked`, `aria-expanded`, label association, what Space and Enter do. That is
  narrower than an audit; `@storybook/addon-a11y` is still not installed.
- **`src/test/dist.test.js` skips when `dist/` is absent.** `build:package` runs before
  `npm test` in both `prepublishOnly` and `release:publish`, so it always runs on the paths that
  matter, but a bare `npm test` on a clean checkout will skip it and say so.

## Why tsup and typescript were added

Two root dev dependencies, added when the repo became a publishable package.

**`tsup`.** The repo had no library build at all — only `build:storybook`, which produces a
static site, not a package. Vite is already here, and `vite build` in library mode was the
obvious thing to reach for first. It was not taken, for the reason the root deployment section
already documents: the root Vite config is load-bearing for the only build that reaches
production, and `framework: null` exists because Vercel applying its Vite preset breaks it. Adding
a library-mode Vite config at the root puts a second, differently-shaped Vite build next to that
one. `tsup` keeps the library build in its own file, `tsup.config.js`, touching nothing Storybook
or Vercel reads. It also emits ESM, CJS and declarations from one entry, which Vite library mode
needs extra plugins to do.

**`typescript`.** Not a language change. It is here because `tsup`'s `dts` step needs a TypeScript
compiler to turn the JSDoc on the `.jsx` sources into `.d.ts`, and because `npm run typecheck` has
to be a command that exists before anything can be asked to run it. The components stay `.jsx`
and `checkJs` stays off. See the "Not set up yet" note above for what the type check does and
does not cover.

Neither solves a problem the existing stack already solved: there was no package build and no
type check to reuse.

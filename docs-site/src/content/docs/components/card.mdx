### `use_when`

**Both sources agree, though only one of them quotes the other.** Figma's
description on the `card` component set reads *"Use a card to group related
content into one surface a user can scan or act on. The card owns the surface,
border, radius and padding; everything inside comes from a card layout placed
in ↳Layout."*

`card.jsx` carries the same two sentences, lightly reworded, in its header
comment. `docs/card.md` states the second half — *"The card owns the surface,
edge, radius and padding. Everything inside comes from a layout placed in the
`↳Layout` slot — the card never styles its contents"* — but, alone among the
six build reports, it does **not** quote the Figma description as a
description. Read live today, the description is there and it says what the
repo says.

### `dont_use_when`

**Both sources agree, in the same words.** Figma: *"Don't nest a card inside
another card."* `card.jsx` says *"Don't nest a card inside a card."*

Neither source states any other case against using a card.

### `variant_intent`

**The shape is agreed.** Two variant properties: `Padding` — `none`, `md`,
`lg`, `xl` — and `State` — `default`, `hovered`, `focused`, `disabled`. Sixteen
combinations, each with a node id in `docs/card.md` and each with a story.

**What each `Padding` step is *for* is stated by neither source.** No variant
inside `65:230` carries a description, and the repo gives only the mechanic.
When a card should be `md` rather than `lg` or `xl` has not been decided.

**`Padding=none` means something specific, and only the repo says it.**
`docs/card.md`: the property sets no padding *on the card*; the 8px still
visible inside belongs to `card/layout/vertical`, which carries
`spacing/padding/sm` of its own in every variant. Figma draws this and does not
explain it.

**The repo states a rule about `State` that Figma does not.** In Figma every
state is a drawn frame. In the repo `state` forces an appearance, and real
behaviour is switched on by supplying `onClick`: the card then takes
`role="button"`, takes focus, answers Enter and Space, and gets live `:hover`
and `:focus-visible` painted from the same tokens. No `interactive` property
was invented — the handler the caller already has to supply is the switch.
Figma has no counterpart to that decision.

**One thing Figma draws that the repo follows and flags.** The `State=disabled`
variants bind title and subtitle to `color/text/primary` and
`color/text/secondary`, the same as every other state, while the surface moves
to `color/bg/disabled`. `color/text/disabled` exists and is unused. The code
follows the node as drawn and `docs/card.md` reports the gap: the intent may
have been to dim the content too, and the subtitle on the disabled surface is
the weakest pairing in the set. Unresolved.

### `placement`

**Neither source states where a Card belongs in a layout**, beyond the
prohibition on nesting.

Two statements sit close to placement without being Card's own. Figma's
`card/layout/horizontal` says *"Don't use it in a narrow column; it needs room
for both sides"* — that is the layout's constraint, not the card's. And
`docs/card.md` records a repo decision with the same flavour: the component
sets no width at all (`inline-size: 100%`), because every Figma variant is
drawn at 320px only to give the component set a frame, and a card in a product
fills the column it sits in. Width belongs to the caller. The stories pin 320px
purely so they can be compared against the node.

### `pairs_with`

**Figma documents six sub-components of Card, by name and by job:**

| Figma component | What its own description says it is for |
|---|---|
| `card/header` | title, optional supporting line, an Action slot for a button, badge or avatar |
| `card/footer` | optional divider and a slot for the card's actions or meta |
| `card/media` | an image, chart or illustration inside a card |
| `card/layout/vertical` | stacks header, body and footer — *"the default arrangement used across Lumo screens"* |
| `card/layout/horizontal` | media or chart left, header and body right |
| `card/layout/metric` | a single KPI — label, large value, and a ↳Badge slot for the change |

**The repo built three of those six, plus the card itself.**
`src/components/card/` contains `card`, `cardHeader`, `cardFooter` and
`cardLayoutVertical`. There is no `cardMedia`, no `cardLayoutHorizontal` and no
`cardLayoutMetric`. `docs/card.md` lists the four files it built and does not
record the three Figma components it did not. This is the largest Figma/repo
divergence across the six components documented here.

**Figma says a Button or a Badge goes in the header's Action slot; the repo
never puts one there.** `card.stories.jsx` imports only `Card` and
`CardLayoutVertical`, and fills both the header action slot and the footer row
with a dashed placeholder. So the pairing is documented in Figma and not
demonstrated in code. (`emptyState.stories.jsx` does import `Card`, to show
where an empty state lives — the pairing exists in the repo, from the other
side.)

### `required_tokens`

Read live from `get_variable_defs` on `65:230` and from the five stylesheets in
`src/components/card/`. The two sources carry the same set, with the exceptions
noted below.

| Property | Token |
|---|---|
| Surface | `color/bg/base`; `color/bg/disabled` when disabled |
| Edge | `color/border/primary/{default,hovered,focused}`, `color/border/disabled` |
| Edge width | `border/width/default`, `border/width/focused` |
| Corner radius | `border/radius/card` |
| Card padding | `spacing/padding/{md,lg,xl}` |
| Layout padding | `spacing/padding/sm` |
| Gaps | `spacing/gap/{xs,sm,md}`, `spacing/gap/horizontal/{sm,md}` |
| Title | `Heading/H5` on `color/text/primary` |
| Subtitle | `Body/Body3` on `color/text/secondary` |

**Three places the two sources do not line up:**

1. **The disabled edge.** Figma binds `color/border/disabled`; the repo writes
   `--color-border-primary-disabled`. Both resolve to `#dadce7`.
   `docs/card.md` gap 4 reports a related problem from the other direction —
   `color/border/primary/disabled` is *described* in Figma as
   `lumo.semantic.color.border.disabled`, an older path. Whether the node binds
   two different variables or one variable with a stale description is not
   settled by either source, and is not settled here.
2. **`color/bg/surfacePrimary` is bound in Figma and used in the repo, and the
   build report omits it.** The live read on `65:230` returns
   `--lumo-semantic-color-bg-surfacePrimary` at `#f5f6fa`, and
   `src/components/card/` uses `--color-bg-surfaceprimary`. The token map in
   `docs/card.md` does not list it. So this is a gap in the repo's own
   documentation rather than a design/code disagreement — the code and the node
   agree. The same applies to `--body-body3-intense` and `--spacing-gap-lg`,
   both used in the card stylesheets and both absent from the build report's
   map.
3. **The transition.** The repo gives state changes `--motion-duration-fast`,
   and `docs/card.md` lists `motion/duration/fast` as a Figma variable. The
   live read on `65:230` returns no motion variable at all. Either the binding
   sits on a child the node query does not reach, or the duration is the repo's
   addition; neither source settles it.

**`border/style/*` and `motion/easing/*` have no values in the export**, so the
token build skips them repo-wide. `docs/card.md` checked this against Figma and
found that `border/style/solid` and `border/style/dashed` *do* exist in the
`lumo.core` and `lumo.semantic.border` collections of
`Lumo.Token.V1.0.Complete` — so it is an export-scope problem, not missing
design work, and a re-export with those collections selected should fix it with
no designer authoring anything.

### `anatomy`

*The field name is unconfirmed — see the note at the top of this section.*

**Both sources agree on the parts.** A card is a surface and a slot. The card
itself owns the background, the edge, the corner radius and the padding;
everything visible inside arrives through `↳Layout`. In the repo that slot is
`children`, and `cardLayoutVertical` is the layout that normally fills it,
stacking `cardHeader`, a body and `cardFooter` down the card.

`card/header` is a title, an optional supporting line and an Action slot.
`card/footer` is a divider above a right-aligned action row, hidden by default.
Both match their Figma descriptions.

**Where the drawing and the code differ, by decision.** Figma draws the card
edge as an *inside* stroke, which is why the focused variant at 2px is exactly
as tall as the default at 1px. A CSS `border` cannot do that — it would add 2px
to every card and make focus reflow the content. The repo uses
`box-shadow: inset` instead, reproducing the Figma heights exactly, with a
`forced-colors` block restoring a real outline for Windows High Contrast where
box-shadow is dropped.

**One part of the node that is scaffolding, and only the repo says so.**
`_Slot/Content` (`41:21`) is a Figma placeholder whose own description says
never to ship a screen with a slot still showing. It lives in
`card.stories.css`, never in the component. `docs/card.md` also notes that its
text is bound to `color/text/secondary` but carries a fallback of `#bfc2cf`,
which is `color/border/primary/default` — cosmetic, placeholder-only, and a
sign the binding was changed without the fallback following.

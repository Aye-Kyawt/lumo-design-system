### `use_when`

**Both sources agree, in the same words.** Figma's description on the
`progress` component set reads *"Use progress to show how far along a
measurable thing is — a score against a target, an initiative's completion, a
multi-step flow."* `progress.jsx` and `docs/progress.md` both quote it
verbatim.

The decided part is **measurable**: progress is for a quantity someone can
name, not for the passage of time.

### `dont_use_when`

**Both sources agree, in the same words.** Figma: *"Don't use it for an unknown
wait; use Spinner instead."* The repo quotes the same sentence.

**The replacement exists in Figma and not in the repo.** `spinner` is a
published component set in the Lumo.Web library — *"Use a spinner for a wait
with no known shape or duration"* — and it in turn points at `skeleton` for a
wait with a known layout. Neither `spinner` nor `skeleton` exists in
`src/components/`, so the two components Progress's documentation routes a
developer towards are both unbuilt.

**A consequence both sources state, in their own way.** There is no
indeterminate variant, and `docs/progress.md` reads that as deliberate rather
than missing: the component description sends the unknown wait to Spinner, so
an indeterminate bar would be the wrong component rather than an absent
feature.

### `variant_intent`

**The shape is agreed.** Two variant properties: `Status` — `brand`,
`positive`, `warning`, `negative` — and `Size` — `sm`, `md`. Eight variants,
each with a node id in `docs/progress.md` and each with a story. Both sources
agree that each property changes exactly one thing: `Status` the indicator
colour, `Size` the track height (6px at `sm`, 8px at `md`).

**What each `Status` *means* is not stated by the Lumo.Web node, and the repo
does not state it either.** No variant inside `69:1151` carries a description,
and `progress.jsx` says only that `status` *"picks the indicator colour.
Nothing else changes."* When a bar should be `warning` rather than `negative`
has not been decided for the web library.

**It has been decided for two sibling platform libraries, and they do not
agree with each other.** This is worth recording precisely, because it is the
nearest thing to a stated rule that exists anywhere:

| Library | What its `progress` description states |
|---|---|
| `Lumo.Mobile.Component.V1.0.Complete` | *"Tone: primary default, positive on track/complete, warning slipping, negative at risk."* |
| `Lumo.AdminSystem.Component.V1.0.Complete` | *"Tone=danger above 90% utilisation or when blocked; warning when at risk."* |

Three things to notice before anyone copies either into the web component.
They call the property **`Tone`**, where the web set calls it `Status`. Mobile
names the fourth value **`negative`** and Admin names it **`danger`** — and
Lumo.Web's *Badge* uses `Danger` while Lumo.Web's *Progress* uses `negative`,
so the two spellings are both live in the system. And the two descriptions
disagree about what the at-risk value is: Mobile says `negative` is "at risk",
Admin says `warning` is "at risk" and `danger` is blocked or over 90%. **None
of this is Lumo.Web documentation and none of it has been adopted here.**

**When to use `sm` rather than `md` is stated by neither source.**

**Why there are no interaction states, and both sources agree on it.** The set
defines no hovered, pressed, focused, disabled, error or loading variant.
`docs/progress.md` treats that as correct: progress is an output, not a
control, so it takes no click handler and is not focusable. `negative` covers
the failing case as a *status*, not as an error state of a control.

**One illustration that is not a rule.** The repo's `In context` story shows
positive at 100%, brand at 72%, warning at 41% and negative at 12%. That is a
story, not a stated mapping, and neither source states it as one.

### `placement`

**Progress's own description says nothing about placement in either source.**

Two Figma siblings do, and one of them is an actual prohibition —
`learning/video-player`: *"Don't put the progress bar inside it; that sits
below as its own element."* `kanban/card` lists *"a real progress instance"*
among its parts, and `learning/lesson` names progress as one of the four
pieces of the lesson layout. Those are statements by those components about
themselves, listed as evidence rather than promoted into Progress's own rule.

**Both sources agree the component is fluid, which is a placement fact of a
kind.** Every Figma variant is drawn in a 280×36 frame, but inside it the label
is full-width, the row is full-width and the track is a flex child taking the
remaining space. `docs/progress.md` reads that as a canvas frame rather than a
constraint and builds the component fluid; the stories pin 280px only so it can
be put side by side with the node.

### `pairs_with`

**Figma, from sibling documentation.** `kanban/card` and `learning/lesson`
each place a real progress instance. `spinner` and `skeleton` are named as
alternatives, not as pairs. `stepper` is the closest neighbour in meaning —
*"Use a stepper to show progress through a multi-step flow"* — which overlaps
Progress's own *"a multi-step flow"*; **neither description says which to reach
for when both would fit**, and that is an unresolved overlap rather than a
pairing.

**Repo.** `progress.stories.jsx` imports nothing but `Progress` itself.
Nothing in `src/components/` imports Progress. So no pairing is demonstrated
in code, and the two hosts Figma documents (`kanban/card`, `learning/lesson`)
have no code at all.

### `required_tokens`

Read live from `get_variable_defs` on `69:1151` and from `progress.css`. The
two sources carry the same set.

| What | Token |
|---|---|
| Label | `Label/Label1` on `color/text/primary` |
| Value | `Body/Body3` on `color/text/secondary` |
| Label → row gap | `spacing/gap/xs` |
| Track → value gap | `spacing/gap/horizontal/sm` |
| Track fill | `color/bg/surfaceSecondary` |
| Indicator | `color/bg/{primary,positive,warning,negative}/idle` |
| Track and indicator radius | `core/border/radius/full` — see below |

**Three values could not resolve to a *semantic* token, and all three are
design gaps rather than build shortcuts:**

1. **`Size` is the whole point of the property and neither value is bound.**
   The node draws 6px at `sm` and 8px at `md`, both raw numbers. No token in
   the system is near them: the core size scale starts at 12, and the semantic
   size families are `icon`, `control`, `avatar`, `touchTarget` and `layout` —
   none of which means "the height of a progress track". Snapping to the
   nearest step was not available either, because the nearest to 6 is 4, which
   would make the two sizes read as 4/8 rather than 6/8 when the height is the
   *only* thing `Size` changes. The repo composes both heights from core
   spacing primitives exactly, isolated in one custom property per size. What
   would close it: `size/progress/sm` = 6 and `size/progress/md` = 8, with the
   node's `Track` frame bound to them.
2. **The radius binds a core token, skipping the semantic layer.** `Track` and
   `Indicator` are both bound to `core/border/radius/full` — confirmed live
   today. The semantic radii that resolve to the same 999 are
   `border/radius/chip` and `border/radius/avatar`; a progress track is
   neither, so borrowing one would be a lie about meaning dressed as a fix. The
   repo reproduces the binding the node actually has. What would close it: a
   `border/radius/progress` or a shared `border/radius/pill`.
3. **The fill cannot animate.** All five `motion/easing/*` tokens are declared
   in the export with no value in any mode, so `build-tokens.js` emits no
   `--motion-easing-*` property at all. The node binds no easing either, so
   nothing was dropped from the design — but a bar whose fill moves is the
   component in this system most likely to want one, and it cannot have one.
   The repo does nothing: the fill snaps, because a substituted cubic-bezier
   would be a design decision taken by an engineer.

**The spacing and type tokens are mode-dependent**, which is the tokens
working rather than a defect: `gap/xs` is 4 in web and mobile and **2** in
admin, `gap/horizontal/sm` is 8 and **4**, and `fontSize/sm` is 12 in web and
admin and **13** in mobile. So Progress is visibly tighter in admin and
slightly larger-set in mobile. The two track heights are *not* mode-dependent,
which is a side effect of gap 1 rather than a decision.

### `anatomy`

*The field name is unconfirmed — see the note at the top of this section.*

**Both sources agree on the parts.** A `Label` text layer above a `Row`; the
`Row` holds a `Track` and a value text layer; the `Track` holds an
`Indicator`. Figma's four non-variant properties map one-to-one onto the
repo's props — `Label` and `Value` are booleans that show or hide the two text
layers, `Label text` and `Value text` carry their strings.

**None of those parts is a Figma component.** They are plain frames inside each
variant, the way Badge's `Label` is a plain text layer. So Progress ships as
one file with no sub-components and `Composes` in the registry is empty — both
sources agree.

**The node's own fill disagrees with the node's own value text.** Every variant
draws `Indicator` at a fixed **158px** while the value text reads **72%**; the
track in that layout is about 246px, so the drawn fill is about **64%**. The
two cannot both be right. `docs/progress.md` records this as unfillable rather
than as a bug — a static Figma frame has no way to express "the fill follows
the number". The repo drives the fill from `percent`, so 72% renders at 72%,
and **the coded component will therefore not match a pixel measurement of the
node's indicator**. That is correct, and it is the kind of thing QA will
measure.

**One prop the node has no property for.** `percent`, the number itself.
Figma's `Value` is the boolean that shows the percentage *text*, so the number
needed a different name; it is registered in
[`docs/naming-conflicts.md`](https://github.com/Aye-Kyawt/lumo-design-system/blob/main/docs/naming-conflicts.md).

**Accessibility, stated by the repo and not drawn in the node.**
`role="progressbar"` sits on the **track**, not on the wrapper — a
progressbar's contents are not exposed to assistive technology, so putting the
role on the wrapper would swallow the label and the value text.
`aria-valuenow` / `-valuemin` / `-valuemax` carry `percent` clamped to 0–100;
`aria-labelledby` points at the label line, and when `label` is false the bar
takes `aria-label={labelText}` so turning the visible line off never leaves it
unnamed. In forced-colours mode, where every background is dropped and the
meaning here *is* the fill, the track takes a `CanvasText` outline and the
indicator is painted `Highlight`; the `Status` distinction is lost in that mode
and the value text carries the number.

## API and the full matrix

The component's documented API is its props — `status`, `size`, `label`,
`labelText`, `value`, `valueText` and `percent`. The eight variants with their
node ids, the full token table, the per-mode measurements and the four design
gaps are in the build report,
[`docs/progress.md`](https://github.com/Aye-Kyawt/lumo-design-system/blob/main/docs/progress.md).

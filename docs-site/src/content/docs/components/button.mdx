### `use_when`

**Both sources agree, in the same words.** Figma's description on the `button`
component set reads *"Use this component when need CTA."* `button.jsx` and
`docs/button.md` both quote that sentence verbatim as the component's reason to
exist.

Neither source goes further. What counts as a CTA, and which of the three
`Type` values a given call to action should take, is unstated in both — see
`variant_intent`.

### `dont_use_when`

**Both sources agree, in the same words.** Figma: *"Don't use it for opening
external link."* The repo quotes the same sentence in `button.jsx` and
`docs/button.md`.

**Neither source says what to use instead.** The Lumo.Web library has no Link
component — searching it returns only an `Additional links` set carrying no
description at all — and `src/components/` has no link component either. So
"not a button" is decided and "then what" is not.

### `variant_intent`

**The shape is agreed.** `Type` — `fill`, `outline`, `transparent`. `State` —
`default`, `hovered`, `focused`, `disabled`, `error`. Fifteen combinations;
`docs/button.md` carries the node id of every one, and every one has a story.

**What each `Type` is *for* is stated by neither source.** Figma's description
covers the set; no variant inside `26:1665` carries a description of its own.
The repo describes mechanics only — `button.jsx` says *"Type picks the skin;
State picks the colours within it."* Which type a primary action, a secondary
action or a destructive action should take has not been written down anywhere.
It is a design decision and it has not been made.

**One thing the repo states that Figma does not.** In Figma every state is a
drawn frame. In the repo `state` *forces* an appearance while the real DOM
behaviour runs underneath: left at `default` the button still hovers, takes
focus, answers Enter and Space, and goes genuinely inert under
`state="disabled"`. `docs/button.md` records this under "`state` forces, the DOM
does the rest".

**One thing Figma draws that the repo deliberately departs from.**
`transparent/focused` (`29:1800`) draws no border and no ring — the variant is
distinguished only by a darker label, which fails WCAG 2.4.7 for a focusable
control. The repo reproduces the node exactly under `state="focused"` so it can
be compared, but gives *real* keyboard focus the ring `fill` and `outline`
already use. Both behaviours are intentional, and the node is unresolved: a
designer decides what transparent focus looks like.

### `placement`

**Neither source states where a Button belongs in a layout.** Button's own
Figma description says nothing about placement, and neither does the repo.

Other components in the Figma library place one, in their documentation rather
than in Button's: `card/header` has *"an Action slot for a button, badge or
avatar"*, `table/cell` says *"Drop text, a badge, an avatar, a checkbox or a
button into the ↳Content slot"*, `chat/composer` is *"a text field and a real
Button to send"*, and `tab` says *"Don't use a tab to trigger an action — that
is a Button."* Those are statements by those components about themselves. They
are listed here as evidence, not promoted into Button's own placement rule.

### `pairs_with`

**Figma, from sibling documentation.** `empty-state` (*"always give the
action"*), `card/header` (Action slot), `card/footer` (*"a slot for the card's
own actions or meta"*), `table/cell`, `chat/composer`, and `calendar/month`
(*"Pair it with time-slot buttons once a date is chosen"*).

**Repo.** `emptyState.stories.jsx` is the only place in `src/components/` that
imports the real `Button`, and it puts it in the `↳Action` slot — which matches
Figma's empty-state documentation exactly.

**Where they part company.** Figma documents a Button in the card header and
footer slots; the repo's card stories fill both slots with a dashed placeholder
and never import Button there. So that pairing is documented in Figma and not
demonstrated in the repo.

### `required_tokens`

Read live from `get_variable_defs` on `26:1665` and from `button.css`. Both
sources carry the same set, and `docs/button.md` has the full state-by-state
map. Shared by every variant:

| Property | Token |
|---|---|
| Padding and gap | `spacing/padding/sm` |
| Corner radius | `border/radius/input` |
| Label type | `Button/Button1` |
| Icon size | `size/icon/md` |
| Edge width | `border/width/default`, `border/width/focused` |

Per state the component binds `color/bg/primary/{idle,hovered,pressed}`,
`color/bg/primary/tonal/idle`, `color/bg/base`, `color/bg/negative/idle`,
`color/bg/disabled`, the matching `color/text/*` and `color/icon/*` roles, and
`color/border/{primary/focused, brand/hovered}`.

**Three places the two sources do not line up:**

1. **The aqua label token.** The Figma MCP returns a single
   `--lumo-semantic-color-text-accent-aqua` at `#16bee3`; the repo binds
   `--color-text-accent-aqualight`. `docs/button.md` gap 3 records that the
   library holds *both* `color/text/accent/aqua` (`#176e82`) and
   `color/text/accent/aquaLight` (`#16bee3`) **carrying identical
   descriptions**, and that the MCP collapses them to one name. Read live
   today, it still does. Unresolved — the descriptions need to be made
   distinct before this traps someone else.
2. **The disabled edge.** Figma binds `color/border/disabled` (`#dadce7`) on
   the node; the repo writes `--color-border-primary-disabled`. Both resolve to
   `#dadce7`. Not resolved here.
3. **The transition.** The repo gives every variant `--motion-duration-fast`.
   `get_variable_defs` on `26:1665` returns no motion variable at all, so the
   transition is the repo's addition and the node binds nothing for it.

`docs/button.md` additionally reports three bindings in the node that use a
token from the wrong family — icon tokens carrying the outline border, a
background token colouring the `transparent/focused` label, and a padding token
driving the flex gap. All three are design gaps, reported and not filled in.

### `anatomy`

*The field name is unconfirmed — see the note at the top of this section.*

**Both sources agree on the parts.** One box: optional leading icon, label,
optional trailing icon, laid out in a row with `spacing/padding/sm` as both the
padding and the gap, on a `border/radius/input` corner. Figma's four
non-variant properties map one-to-one onto the repo's props — `label` (string),
`text`, `iconLeft`, `iconRight` (booleans).

**Where the drawing and the code differ, by decision.** Figma draws the edge as
a stroke, outside on four outline variants (120×38, 1px) and inside on
`outline/focused` (118×36, 2px) — the two cannot both be right, and taken
literally an outline button would grow beside a fill button and then shrink the
moment it takes focus. The repo draws every edge as `box-shadow: inset`, so all
fifteen variants are one box and nothing moves. The node still needs fixing
either way.

**One part the repo names and Figma does not.** The icons are Material Symbols
font glyphs loaded from the Google Fonts CDN, not SVGs in the repo; Figma names
the icon layer `Icon/add`. An icon-only button (`text={false}`) keeps `label` as
its `aria-label` and marks the glyph spans `aria-hidden`, so the ligature text
never leaks into the accessible name — a repo decision with no counterpart in
the node.

## API and the full matrix

The component's documented API is its props, described above under `anatomy`
and `variant_intent`. The complete fifteen-variant matrix with node ids, the
state-by-state token map and the six design gaps are in the build report,
[`docs/button.md`](https://github.com/Aye-Kyawt/lumo-design-system/blob/main/docs/button.md).

Two prop names could not be taken straight from Figma and are recorded in
[`docs/naming-conflicts.md`](https://github.com/Aye-Kyawt/lumo-design-system/blob/main/docs/naming-conflicts.md):
`htmlType` carries the DOM `type` attribute because Figma's variant already owns
`type`, and the `↳iconLeft` / `↳iconRight` swap slots became `iconLeftName` /
`iconRightName`, taking a Material Symbols glyph name.

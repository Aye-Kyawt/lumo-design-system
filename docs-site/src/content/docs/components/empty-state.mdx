### `use_when`

**Both sources agree, in the same words.** Figma's description on the
`empty-state` component set reads *"Use an empty state when a list, card or
page has nothing to show — no results, nothing created yet, a failed load, or
no permission."* `emptyState.jsx` and `docs/emptyState.md` both quote it
verbatim.

Four causes are named and they are not the same kind of thing — a filter that
matched nothing, a collection never started, a request that failed, and a
permission the user does not have. Neither source says whether those four
should look different from each other, or read as the same component with
different text. See `variant_intent`.

### `dont_use_when`

**This is the one component of the six whose "don't" is not a substitution.**
Figma: *"Don't leave the user without a next step; always give the action."*
The repo quotes the same sentence.

That is a rule about *how* to use an empty state, not about when to reach for
something else. **Neither source names a case where an empty state is the
wrong component.** The contract field is answered — there is a stated
prohibition — but it does not answer "use X instead", because nobody wrote
that.

One sibling in Figma states the inverse, which is the closest thing to a
boundary: `chat/thread` says *"Don't show a thread with no conversation
selected; use Empty State instead."*

### `variant_intent`

**The shape is agreed.** One variant property, `Size`, with two values: `sm`
(`94:7`) and `md` (`94:15`). Both sources agree the two differ only in the
medallion size and the two type styles — the four-row column is otherwise the
same. Three further properties are not variants: `Description` (boolean),
`Action` (boolean), and the text properties.

**When to use `sm` rather than `md` is stated by neither source.** No variant
inside `94:1862` carries a description, and `emptyState.jsx` says only that
`size` *"picks the medallion size and the title/description type styles."*
The node draws `sm` at 360px wide and `md` at 520px, which hints at a narrow
container versus a page — but that is an inference from a frame width, not a
statement, and neither source makes it.

**Nor does either source map the four causes onto anything.** Figma names no
results, nothing created yet, a failed load and no permission in `use_when`,
and then gives one variant property that has nothing to do with them. Whether
a failed load should look different from an empty filter is undecided in both
places.

**The set draws no interaction state, and both sources agree that is
correct.** No hovered, pressed, focused, disabled or loading variant exists,
and the repo added none — explicitly the opposite of what Switch did. The
reasoning in `docs/emptyState.md`: an empty state is a static display, and
everything interactive about it is the Button in the action slot, which already
ships all five of its own states. **If the product needs the empty state itself
to have a loading or error skin, the node has to draw it.**

### `placement`

**Both sources state where an empty state goes, and they agree.** Figma's own
description names the three containers — *"when a list, card or page has
nothing to show"*. The repo demonstrates one of them: the `In card` story puts
an Empty State inside a real `Card`.

One sibling adds a fourth container, in its own documentation rather than in
Empty State's: `chat/thread` says a thread with no conversation selected should
show an Empty State instead.

**What neither source states is how it sits in its container** — centred,
full-bleed, with what margin. The repo makes the component fluid
(`inline-size: 100%`) and leaves width to the caller, which is a decision about
sizing rather than a statement about placement.

### `pairs_with`

**Button, and both sources are unambiguous about it.** This is the clearest
pairing of the six components documented here. The Figma `↳Action` slot
(`94:14` / `94:22`) is **empty in both variants**, and the description says
*"always give the action"* — so the node asks for a real Button to be dropped
in rather than drawing one. `emptyState.stories.jsx` imports the real `Button`
and puts it in that slot, and no button styling exists anywhere in
`emptyState.css`.

**Card, in the repo and by implication in Figma.** `emptyState.stories.jsx`
imports `Card` for the `In card` story; Figma's description names a card as one
of the three containers.

**One pairing the repo wanted and could not have, and it is a system gap.**
`emptyStateIcon.jsx` is almost identical to `button/buttonIcon.jsx` and is
*not* an import of it, because `buttonIcon` paints itself from
`--lumo-button-icon`, a custom property only `.lumo-button` defines — used
anywhere else it renders with no colour. `docs/emptyState.md` reports this as a
real gap in the library and explicitly declines to close it, because closing it
means editing Button and an engineer does not edit another component to make
their own work. **The system wants a standalone `icon` component** that takes a
glyph name and inherits its colour; Button and Empty State would both import
it. Neither source has one.

### `required_tokens`

Read live from `get_variable_defs` on `94:1862` and from `emptyState.css`.
**Every colour and every type style in this component resolves to a semantic
token, with no substitution and no borrowing** — the cleanest token story of
the six.

| Where | Token |
|---|---|
| Column gap | `spacing/gap/md` |
| Medallion fill | `color/bg/brand/subtle` |
| Glyph colour | `color/icon/brand` |
| Glyph size | `size/icon/md` |
| Title colour | `color/text/bold` |
| Description colour | `color/text/secondary` |
| Title / description, `sm` | `Body/Body6-Intense` / `Body/Body3` |
| Title / description, `md` | `Heading/H4` / `Body/Body2` |

The four composite type tokens match their Figma styles declaration for
declaration — weight, size, line height and family — so nothing was
approximated.

**Three geometry values bind nothing in the node**, and the live read confirms
all three today:

1. **The medallion corner binds a core token.** Figma binds
   `core/border/radius/full` directly. The build skill says a component
   reaching for a base token has skipped the semantic layer — but here it is
   the *design* that reaches for it, not the build, so the repo reproduces the
   binding exactly. The semantic layer already has two aliases of the same 999,
   `radius/avatar` and `radius/chip`; substituting one would be the documenter
   or the engineer deciding which meaning the medallion has. What would close
   it: `semantic.border.radius.medallion`, or point the node at
   `radius/avatar`.
2. **The medallion sizes bind nothing.** 56px (`sm`) and 72px (`md`), with
   nothing on the semantic size scale that fits — `size/avatar/xl` is 64,
   `size/icon/xl` is 32, and `size/layout/sidebarCollapsed` is 72 but means a
   collapsed sidebar. The repo uses the core primitives `size/56` and
   `size/72`, exact in all three platform modes. What would close it:
   `semantic.size.medallion.sm` / `.md`.
3. **The frame widths and the description inset bind nothing, and no token
   carries them.** 360px / 520px frames; a 320px description inside the 360
   frame (20px each side) and 420px inside the 520 (50px each side). Neither
   inset matches the other and none of the four numbers is a token at any
   layer. The repo makes the component fluid and lets the description fill its
   container. **If the inset is a measure constraint to stop the line getting
   too long, it wants a token and probably the same one in both sizes; if it is
   just how the frame was drawn, the node should say so.** Undecided.

**The type and gap tokens are mode-dependent**, which is the tokens working:
`gap/md` is 16 in web and mobile and **12** in admin, and every one of the four
font sizes moves between modes. Every colour, both medallion sizes and the icon
size are identical in all three, so the component is the same shape everywhere
and simply tightens on admin.

### `anatomy`

*The field name is unconfirmed — see the note at the top of this section.*

**Both sources agree on the parts: a four-row column.** A medallion holding an
icon, a title, an optional description, and the action slot. Figma's
properties map one-to-one onto the repo's props, with one renaming noted
below.

**The most important part is the one Figma does not draw.** `↳Action`
(`94:14` / `94:22`) is an empty slot in both variants, and the real `Button`
goes into it as `children`. This is the first molecule in the library and the
first component whose load-bearing piece is a hole.

**And that hole is the size of the biggest disagreement here.** The empty slot
measures exactly **100×100** in both variants, which is 100px of the node's
published height — `sm` is 360×256 and `md` is 520×284, and a real Button is
36px tall. So the node's own sizes are about 100px taller than any empty state
with a real button in it will ever be. The repo sizes the slot by its contents,
making an `sm` empty state about 192px rather than 256px. `docs/emptyState.md`
declines to decide this: rendering a fixed 100×100 box would put a 36px button
in the top-left of a large empty square, which is plainly not what the design
means — but "plainly" is a judgement and the number is in the node. **A
designer should either fill the slot in Figma with the Button component or
shrink it to hug.** Until then, measuring the overall frame height against the
node will show a difference, and this is it.

**One prop the node does not define.** `titleAs`, defaulting to `'p'`. The
node's title is a text layer in both variants, so `<p>` is the faithful render
— but the `md` title uses `Heading/H4`, which signals heading intent, and an
empty state that owns a region of a page with no heading in it is a hole for a
screen reader user. `titleAs` is an opt-in escape hatch, not a visual change:
left alone, the component renders exactly what the node draws.

**One prop renamed because the node spells two properties the same.** The set
has both a boolean `Description` and a text `Description`; the text one became
`descriptionText`. Recorded in
[`docs/naming-conflicts.md`](https://github.com/Aye-Kyawt/lumo-design-system/blob/main/docs/naming-conflicts.md),
along with `children` for the `↳Action` slot, since `action` is taken by the
boolean.
